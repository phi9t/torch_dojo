# MoE implementation survey: model contracts and training systems

Checked October 6, 2026. This is a primary-source comparison for original dojo workouts, not an implementation spec supplied by the model authors. **Model math**, **training policy**, and **released inference code** are kept separate: a checkpoint config or an inference demo cannot prove how a private pretraining loop handled capacity, load balancing, or expert parallelism. Related local work: [basic top-k MoE](../../dojo/0028_moe.py) and the [Olmo-core 3 spike](olmocore3-dojo-spike.md).

**Conclusion:** The existing dojo covers selected-logit top-k routing but leaves out several core MoE contracts. The best portable path is a concept-first set of eight small workouts: router variants, shared experts, route counts, balancing, bias feedback, capacity, dispatch/combine, and one training step. DeepSeek and Qwen variants provide contrasting model rules; Olmo-core and public training frameworks make the workload consequences concrete. Keep GPU kernels and distributed throughput as electives.

The selection criterion is a distinct, inspectable MoE mechanism that a learner can implement and verify on small tensors. Mixtral and gpt-oss anchor the common top-k path; DeepSeek and Qwen show how router math and shared branches vary; Olmo-core, MegaBlocks, and Megatron-Core expose training and dispatch choices. This is a mechanism survey, not an exhaustive list of MoE checkpoints.

## Deconstruction and exercise seams

### 1. Router normalization is a model contract

V2's equations compute `p = softmax(logits)` across all routed experts and output `sum(selected p_i * expert_i(x))`, so truncation removes probability mass. V3 computes `s_i = sigmoid(logit_i)` independently, selects by `s_i+b_i`, then uses `s_i / sum_selected(s_j)` for output weights; bias is absent from the mixture coefficient. Qwen3 also normalizes selected weights, but its score **before selection** is a full softmax, so changing a nonselected logit can change pre-selection scores and load-loss statistics even if the selected normalized mixture is algebraically unchanged. This last observation is an inference from the cited equations/code. [V2 Eqs. 20–22](https://arxiv.org/html/2405.04434#S2.SS2.SSS1), [V3 Eqs. 12–16](https://arxiv.org/html/2412.19437#S2.SS1.SSS2), [Qwen3 compatible router](https://github.com/huggingface/transformers/blob/main/src/transformers/models/qwen3_moe/modeling_qwen3_moe.py).

**Workout:** Given fixed expert outputs and logits, implement three score/normalization contracts behind one explicit mode. Baseline: top-k selected softmax like current #28. Follow-up: V2 full-softmax truncate versus Qwen3 selected renormalization; show a numeric output difference. Production: V3 sigmoid, bias-for-selection-only, route scale, and finite-difference gradients away from top-k ties. This is distinct from #28 because selection probability mass and bias placement are the object of the lesson.

### 2. Shared experts are three different equations

DeepSeek-V2/V3 add shared FFN output without a token-dependent shared gate. Qwen3 has no shared branch. Qwen3-Next's compatible forward adds `sigmoid(w_shared·x) * shared_expert(x)` to the normalized routed mixture. Qwen3.5 and Qwen3.6 checkpoint configurations retain a shared branch, while their compatible Qwen3.5 forward uses the same sigmoid-gated pattern. Thus a generic `shared_expert=True` switch would hide materially different contracts. [V2 Eq. 20](https://arxiv.org/html/2405.04434#S2.SS2.SSS1), [V3 Eq. 12](https://arxiv.org/html/2412.19437#S2.SS1.SSS2), [Qwen3 report §2](https://arxiv.org/html/2505.09388#S2), [Qwen3-Next compatible forward](https://github.com/huggingface/transformers/blob/main/src/transformers/models/qwen3_next/modeling_qwen3_next.py), [Qwen3.5 config](https://huggingface.co/Qwen/Qwen3.5-397B-A17B/blob/main/config.json).

**Workout:** Compose fixed routed and shared scalar experts by hand, then implement ungated and sigmoid-gated shared paths. Test gate saturation, shared branch gradients, zero routed contribution, and the fact that the shared branch is evaluated for every token. The existing [Olmo shared-expert collapse proposal](olmocore3-dojo-spike.md#5-collapse-always-active-shared-swiglu-experts) applies to *ungated* shared experts; a distinct input-dependent gate blocks that algebraic collapse in general.

### 3. Balance scope and controller timing

V2's three losses target different histograms: per expert, per device compute, and whether a token is sent to a device. V3 uses whole-step requested load to update a persistent expert bias **after** the step, while retaining a small sequence loss. Qwen3 states a global-batch load-balancing loss. The Qwen team's separate method paper explains synchronization of small expert-count vectors across parallel groups and a running buffer across gradient-accumulation microbatches; the buffer is an **approximation** to the whole-batch objective, not proof that Qwen3's private trainer uses that exact code. [V2 Eqs. 23–31](https://arxiv.org/html/2405.04434#S2.SS2.SSS3), [V3 Eqs. 16–20](https://arxiv.org/html/2412.19437#S2.SS1.SSS2), [Qwen3 report §2](https://arxiv.org/html/2505.09388#S2), [Qwen team balance method §3](https://arxiv.org/html/2501.11873#S3).

**Workout:** Use two domain-specific microbatches whose separate hard loads are imbalanced but whose union is balanced. Compute microbatch-mean versus global hard-count/soft-score loss, then implement (a) an exact two-pass global variant and (b) a prefix-count approximation. Show by a numeric counterexample that the two losses and gradients need not match. Follow with post-batch V3 bias updates and a test that microbatching does not change update frequency. This extends the [Olmo route accounting/bias proposals](olmocore3-dojo-spike.md#4-router-bias-as-a-post-batch-controller) rather than duplicating them.

### 4. Locality, capacity, and dropping are independent

V2's `M`-device preselection bounds the number of destinations, but it does not guarantee equal receive load; hence its separate communication loss and per-device admission budget. V3 changes locality from **device** to **node**, scores a node by the sum of its best `K/M` experts, and reports dropless training and inference. The released V3 gate uses biased scores for group ranking, scores groups by the sum of their best two experts when the bias is present, masks excluded groups, and gathers output weights from original unbiased scores. The published 671B config uses 8 groups and allows 4. This is an inference-code description, while the node and dropless training policy is report evidence. [V2 §§2.2.2–2.2.4](https://arxiv.org/html/2405.04434#S2.SS2), [V3 §2.1.2](https://arxiv.org/html/2412.19437#S2.SS1.SSS2), [V3 inference gate](https://github.com/deepseek-ai/DeepSeek-V3/blob/main/inference/model.py#L2737-L2779), [V3 config](https://github.com/deepseek-ai/DeepSeek-V3/blob/main/inference/configs/config_671B.json).

**Workout:** Given expert scores and expert-to-device/node ownership, implement unrestricted, V2-style max-device-first, and V3-style sum-of-top-`K/M`-per-node routing. Test a case where highest individual expert and best aggregate node disagree, count unique destinations per token, and separate requested load from kept load. Add deterministic device-capacity admission as a follow-up, using [Olmo shared rank capacity](olmocore3-dojo-spike.md#2-shared-destination-rank-capacity) as the contrasting policy; do not assert a CPU toy reproduces DeepSeek throughput.

### 5. Post-training route replay

DeepSeek-V3.2 reports **Keep Routing** in RL: record expert paths used by the sampler and force the training pass through those paths, because implementation differences or policy updates can otherwise change active experts for the same trajectory. The paper says it has used this since DeepSeek-V3-0324. This is a distinct issue from matching sampled token IDs or importance ratios. [V3.2 §3.1](https://arxiv.org/html/2512.02556#S3.SS1).

**Workout:** Run a tiny router at parameters `theta_old`, store expert IDs, then update the router and compare recomputed versus replayed routes. Assert the replayed forward uses the same expert parameter subset, validate ID shape/range, and state explicitly whether output mixture weights are recomputed from `theta_new` or stored; the paper does not provide a full public implementation contract for that last choice. This is a later RL/MoE integration exercise, not a prerequisite for MoE basics.

### 6. V4 routing variants and training stability

DeepSeek-V4 changes learned expert affinity from sigmoid to `sqrt(softplus(z))`, uses token-ID hash routing for the initial three MoE layers, and removes V3's node limit. The V4 report says the series still uses a batch-end bias controller plus a slight sequence loss. It reports **Anticipatory Routing** as a recovery mode for loss spikes: route indices for step `t` come from older parameters while the step's features use current parameters. It also clamps expert SwiGLU inputs to control outliers. These are V4-specific MoE mechanisms; hybrid attention and manifold-constrained residual connections are separate architectural changes. [V4 §§2.1, 4.2.3](https://arxiv.org/html/2606.19348#S2.SS1).

**Workout A:** Implement three positive affinity functions and fixed top-k selection; compare output scale and derivatives for large positive/negative logits. Add a token-ID lookup for the first few layers and show that two contexts with the same token ID choose the same experts while their computed mixture weights can differ. The report states a predefined hash function, not its exact public construction, so the exercise must supply one.

**Workout B:** Cache route IDs from a lagged router, run current features through those selected experts, and compare to current-parameter routing. Check stale route validity and parameter-gradient support. This has a similar replay mechanism to V3.2 Keep Routing but a different purpose and timing: V3.2 targets sampler/trainer RL consistency; V4 targets pretraining loss spikes. A CPU exercise can validate semantics, not reproduce stability or the paper's reported overhead. [V3.2 Keep Routing](https://arxiv.org/html/2512.02556#S3.SS1), [V4 Anticipatory Routing](https://arxiv.org/html/2606.19348#S4.SS2.SSS3).

## Proposed dojo learning path

The first runnable batch should use portable PyTorch routing and training exercises. This follows the user's scope choice on October 6, 2026. These are **authored** small-tensor exercises, not reproductions of full models. Put one editable `# %% [answer]` section in each top-level question script and its reference plus staged verifiers in the neighboring `_eval.py`, as the existing dojo does. Each verifier should reject a plausible wrong implementation.

| Order | Workout contract | Baseline → follow-up → production checks | Prerequisite |
| --- | --- | --- | --- |
| 1 | **Router semantics:** logits, optional selection bias, top-k, returned selected weights. | Selected-logit softmax → full-softmax truncation versus selected renormalization → sigmoid affinities, bias only in selection, route scale, stable ties and gradients. | #28. |
| 2 | **Shared branch:** routed outputs plus absent, ungated, or sigmoid-gated shared output. | Hand-computed sum → token-dependent gate → gradient and empty-token checks; no accidental normalization of the shared branch. | #15, #28. |
| 3 | **Route ledger:** IDs, owner rank, keep mask to requested/kept expert and rank counts. | Count routes → include drops → four max/mean imbalance views, zero-total policy, and conservation. | #28. |
| 4 | **Balance objective:** hard counts detached, soft scores differentiable, explicit balance scope. | Switch-style scalar → six-token gerrymandering counterexample → local versus combined microbatches and gradient checks. | 3. |
| 5 | **Bias controller:** selected IDs over a full training batch update a persistent bias. | Under/overloaded sign → microbatch accumulation → update timing, output weights from unbiased scores, and no gradient through the bias update. | 3–4. |
| 6 | **Capacity admission:** request matrix, expert ownership, matched integer budgets. | One budget → deterministic partial split and distinct requested/kept metrics → private expert versus shared-rank capacity and drop inequality. | 3. |
| 7 | **Dispatch and combine:** route table to expert-contiguous rows and inverse weighted accumulation. | Exact forward order → duplicate token routes and uneven expert loads → dense-reference gradient parity, no lost or duplicated contribution, bounded intermediate storage. | 1, 3. |
| 8 | **One tiny MoE update:** registered router and expert parameters, a tiny labeled batch, and route diagnostics before and after a step. | Loss and backward → expert starvation case → compare balancing feedback and explain when the measured route histogram changes. | 1–7. |

After those, use **hierarchical device/node-limited routing**, **RL Keep Routing versus V4 anticipatory route caching**, **V4 hash routing and positive affinity**, and **block-scaled expert-weight decoding** as electives. They add distinct constraints, but should not delay the routing and training fundamentals. A real multi-GPU all-to-all, grouped GEMM, MXFP4 kernel, or throughput claim needs a separate hardware-aware experiment with a dense numerical reference and end-to-end measurement. A pure Python simulator checks movement and reduction semantics, not hardware speed. [DeepSeek-V3 systems description](https://arxiv.org/html/2412.19437#S3.SS2), [Olmo-core 3 report](https://allenai.org/papers/olmocore3), [Megatron-Core MoE guide](https://docs.nvidia.com/megatron-core/developer-guide/latest/user-guide/features/moe.html).

## Evidence limits

Do not infer kernel-level performance from Python exercises. V3 reports 64-way expert parallelism, all-to-all dispatch/combine, and DualPipe overlap, but its public inference demo does not expose that training stack. V4 separately reports a wave-pipelined MegaMoE kernel; studying that implementation is a systems elective with its own hardware contract. The Qwen3 report gives no comparable detailed dispatch topology or token-drop rule, so those cells remain **not established**, not silently set to DeepSeek defaults. [V3 §3.2](https://arxiv.org/html/2412.19437#S3.SS2), [V4 §3.1](https://arxiv.org/html/2606.19348#S3.SS1), [Qwen3 report §2](https://arxiv.org/html/2505.09388#S2).
