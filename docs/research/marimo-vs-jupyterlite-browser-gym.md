# Marimo WASM versus JupyterLite for the browser ML gym

Research date: 2026-10-05 (Pacific). This compares **editable, static-hosted, browser-Python** deployments for the [current gym design](../superpowers/specs/2026-10-05-browser-ml-gym-design.md), not server-backed marimo or JupyterLab. Claims below are from project documentation; design consequences are marked **inference**. Neither stack has been prototyped in this repo yet.

## Decision in one paragraph

Marimo deserves serious consideration. `marimo export html-wasm notebook.py --mode edit` gives a statically hosted editable notebook, and its reactive cells, built-in UI, plots, Python source, and explicit expensive-computation controls fit the requested playful lesson surface unusually well. JupyterLite is currently the safer *integration* choice for the spec's custom gym panel, selected solution-cell capture, browser-local attempts, and notebook export because its JupyterLab extension and notebook metadata/model APIs are documented. That is an engineering judgment, **not** evidence that marimo cannot support the workflow. Before committing to either, build one thin `0059` spike that saves two attempts, extracts exact answer source, runs a fresh-worker check, records a hint reveal, and exports/reimports a receipt. Sources: [marimo WASM export](https://docs.marimo.io/guides/exporting/webassembly_html/), [marimo interactivity](https://docs.marimo.io/guides/interactivity/), [JupyterLite frontend extensions](https://jupyterlite.readthedocs.io/en/stable/howto/extensions/frontend.html), [JupyterLab notebook model](https://jupyterlab.readthedocs.io/en/stable/extension/notebook.html), [JupyterLite storage](https://jupyterlite.readthedocs.io/en/stable/howto/configure/storage.html).

## Requirement-by-requirement comparison

| Requirement | Marimo WASM | JupyterLite + Pyodide | Design consequence |
| --- | --- | --- | --- |
| Editable static hosting | `html-wasm --mode edit` opens the editor on a static host; `--mode run` is the read-only app mode. Ordinary directory export needs HTTP, while `--single-file` can open directly but fetches runtime/assets online ([export guide](https://docs.marimo.io/guides/exporting/webassembly_html/)). | Builds a static Jupyter site; Pyodide kernel executes in a browser worker ([overview](https://jupyterlite.readthedocs.io/en/stable/), [kernel guide](https://jupyterlite.readthedocs.io/en/stable/howto/configure/kernels.html)). | Both meet the browser-only Python requirement. Do not confuse marimo's `run` and `edit` export modes. |
| Reactive probes and teaching UI | UI values trigger dependent cells; slider/form/button, accordion/lazy sections, and layouts are built in ([interactivity](https://docs.marimo.io/guides/interactivity/), [layouts](https://docs.marimo.io/api/layouts/), [lazy](https://docs.marimo.io/api/layouts/lazy/)). Plot wrappers support selection flowing back to Python ([plotting](https://docs.marimo.io/guides/working_with_data/plotting/)). | Supports `ipywidgets`, Matplotlib, Plotly, Altair, etc.; Pyodide kernel supplies IPython and inline Matplotlib ([overview](https://jupyterlite.readthedocs.io/en/stable/), [kernel guide](https://jupyterlite.readthedocs.io/en/stable/howto/configure/kernels.html)). Widget callbacks and notebook cell execution must be composed deliberately. | Marimo has the clearer built-in path for parameter-driven plots and progressive lesson controls. Both can render shape/dtype cards written in Python; neither supplies the gym-specific tensor card automatically. |
| Execution semantics | Static analysis builds a cell dependency graph; downstream cells run or become stale. It forbids cross-cell duplicate definitions/cycles and does not track mutation of an object defined in another cell ([reactivity](https://docs.marimo.io/guides/reactivity/), [constraints](https://docs.marimo.io/guides/understanding_errors/)). | Traditional notebook kernel state lets learners execute cells in arbitrary order; the gym's isolated check remains necessary to prove submitted source without scratch-state dependencies ([JupyterLite kernel guide](https://jupyterlite.readthedocs.io/en/stable/howto/configure/kernels.html)). | Marimo reduces stale-output confusion, but its DAG rules may surprise learners implementing stateful SGD across cells. Put training mutation inside one function/cell; use a run button or lazy mode for expensive training ([expensive notebooks](https://docs.marimo.io/guides/expensive_notebooks/)). |
| Notebook/source format | Notebook is a Python `.py` file with `@app.cell` functions; it can run as a script, be edited in Emacs, and be exported to `.ipynb` or a plain Python script ([own editor](https://docs.marimo.io/guides/editor_features/watching/), [scripts](https://docs.marimo.io/guides/scripts/), [Python export](https://docs.marimo.io/guides/exporting/python_script/), [Jupyter export](https://docs.marimo.io/guides/exporting/jupyter_notebook/)). Export to `.ipynb` does not preserve all marimo UI behavior ([migration guide](https://docs.marimo.io/guides/coming_from/jupyter/)). | `.ipynb` is JSON with per-cell `source` and metadata; a namespaced metadata flag can mark answer cells ([nbformat](https://nbformat.readthedocs.io/en/latest/format_description.html)). A JupyterLab extension can read cells and metadata via its notebook model ([model API](https://jupyterlab.readthedocs.io/en/stable/extension/notebook.html)). | Marimo is better as a human-readable canonical lesson file. JupyterLite is better documented for extracting *exact selected answer cells*. For marimo, the gym needs a robust convention/parser or separate answer module; `@app.cell` source is not directly equivalent to a standalone `solution.py` (**inference**). |
| Custom gym chrome and capture | `mo.ui` and `anywidget` support custom **in-notebook** controls ([custom widgets](https://docs.marimo.io/api/inputs/anywidget/)). The reviewed public guides do not document a JupyterLab-like API for adding host-editor panels/commands or reading unsaved editor source from an external gym shell. This is an **unverified integration gap**, not a claimed impossibility. | Frontend extensions reuse JupyterLab's plugin system; notebook model exposes cell metadata and source editing APIs ([extension guide](https://jupyterlite.readthedocs.io/en/stable/howto/extensions/frontend.html), [notebook model](https://jupyterlab.readthedocs.io/en/stable/extension/notebook.html)). | If the dedicated Check/Stop/attempt/result panel is non-negotiable, JupyterLite has lower documented integration risk. A marimo alternative is to put the gym UI inside the notebook and prove source capture in a spike. An anywidget is not itself an editor extension. |
| Packages and runtime | WASM uses Pyodide; NumPy, SciPy and Matplotlib are available, but compatibility is limited to Pyodide/pure Python wheels. PEP 723 dependencies and platform markers help share a notebook with native Python ([WASM guide](https://docs.marimo.io/guides/wasm/)). | Pyodide kernel supports dynamic `piplite`; wheels can be added to its distribution/build, and Pyodide itself can be self-hosted ([kernel guide](https://jupyterlite.readthedocs.io/en/stable/howto/configure/kernels.html), [wheels](https://jupyterlite.readthedocs.io/en/stable/howto/pyodide/wheels.html), [custom distribution](https://jupyterlite.readthedocs.io/en/stable/howto/pyodide/pyodide.html)). | Both need a pinned browser package qualification run for the repo's actual verifiers. Neither runs native PyTorch/CUDA in this browser plan. Marimo's cached Torch-output feature cannot grade newly edited Torch code in Pyodide ([cache limits](https://docs.marimo.io/guides/exporting/webassembly_html/)). |
| Persistence and export | Editable export is documented, but the reviewed static-export guide does **not** promise durable saved attempts or an attempt-history API; marimo calls its public WASM playground ephemeral ([WASM guide](https://docs.marimo.io/guides/wasm/)). It documents notebook downloads/exports; `.py` omits outputs, and `.ipynb` conversion has UI limits ([migration guide](https://docs.marimo.io/guides/coming_from/jupyter/)). Treat save-on-reload behavior for self-hosted edit mode as **unknown until tested**. | Site-created files are stored in browser storage (usually IndexedDB), and can be uploaded/downloaded; storage is tied to browser and site origin ([storage](https://jupyterlite.readthedocs.io/en/stable/howto/configure/storage.html), [using a deployment](https://jupyterlite.readthedocs.io/en/stable/quickstart/using.html)). | Neither gives the spec's append-only receipts, source hashes, assistance log, archive, or reimport for free. Build those in gym code. JupyterLite starts with documented editable file persistence. |
| Fresh isolated check | Marimo's reactive notebook/pytest integration runs within its lesson runtime; that is useful for feedback but does **not** satisfy the spec's fresh-check boundary ([pytest guide](https://docs.marimo.io/guides/testing/pytest/)). | The exploration kernel also does not satisfy the boundary. | Both need a separate Pyodide worker supplied with the captured answer and verifier bundle. Pyodide documents worker execution and interrupt APIs ([worker](https://pyodide.org/en/stable/usage/webworker.html), [interrupt](https://pyodide.org/en/stable/usage/keyboard-interrupts.html)). Worker termination provides the hard Stop path (**architecture inference**). |
| Interrupt and long work | Marimo has a Stop control and can mark expensive dependent cells stale, but its WASM concurrency is cooperative; running Python is not preempted by its process-shaped adapters ([reactivity](https://docs.marimo.io/guides/reactivity/), [WASM limits](https://docs.marimo.io/guides/wasm/)). | Pyodide kernel runs in a worker; Pyodide interrupt buffer requires `SharedArrayBuffer`/cross-origin isolation for cooperative interruption ([kernel guide](https://jupyterlite.readthedocs.io/en/stable/howto/configure/kernels.html), [Pyodide interrupts](https://pyodide.org/en/stable/usage/keyboard-interrupts.html)). | Do not rely on either editor Stop to bound malicious or accidental infinite checks; terminate the separate checker worker on deadline. Test exploration-kernel recovery separately. |
| Offline deployment | `html-wasm --offline` bundles runtime and packages beside exported HTML, but data/remote APIs/widget JS still need local assets; serve over HTTP ([self-host guide](https://docs.marimo.io/guides/publishing/self_host_wasm/)). | Self-contained archive can include a local Pyodide distribution, with additional configuration for kernel assets/packages ([offline guide](https://jupyterlite.readthedocs.io/en/stable/howto/configure/advanced/offline.html)). | Both can be qualified offline. Neither should claim offline until reload with network disabled passes for all 13 labs and widgets. |
| Accessibility and browser testing | Marimo documents current Chrome, Firefox, Edge and Safari support, recommending Chrome for WASM ([WASM guide](https://docs.marimo.io/guides/wasm/)). | JupyterLite inherits JupyterLab UI and supports browser execution ([overview](https://jupyterlite.readthedocs.io/en/stable/)). | Neither source establishes accessibility of *our* hints, tensor cards, plots, keyboard flow, or screen-reader text. Test those in the final UI. Marimo's own `marimo check` and notebook pytest support help author tests but do not replace end-to-end browser acceptance ([WASM lint](https://docs.marimo.io/guides/exporting/webassembly_html/), [pytest guide](https://docs.marimo.io/guides/testing/pytest/)). |
| Native Python / Emacs route | `.py` notebook is directly editable in Emacs; `marimo edit --watch` syncs file edits into the browser. Native execution requires marimo and dependencies ([own editor](https://docs.marimo.io/guides/editor_features/watching/), [scripts](https://docs.marimo.io/guides/scripts/)). | `.ipynb` is portable Jupyter format, but native exercise submission still benefits from a derived `solution.py`; JupyterLite's browser store is not the checkout's filesystem ([nbformat](https://nbformat.readthedocs.io/en/latest/), [storage](https://jupyterlite.readthedocs.io/en/stable/howto/configure/storage.html)). | Marimo has a strong advantage for text-editor lesson authoring. In either route, keep existing `dojo/` verifiers and capstone canonical Python as the native check path. |

## What to prove before switching the design

1. **Source fidelity:** edit two designated answer cells, capture only those cells as importable `solution.py`, hash it, change a cell, and detect that the earlier pass is stale. For marimo, confirm the capture uses a supported interface or a stable generated-source convention rather than reading rendered DOM (**unknown**).
2. **Attempts:** create A and B, reload with a fresh browser session, restore each exact notebook/source and hint/solution reveal history, export/import both, and verify receipt hashes. Marimo static edit mode durability is currently **unverified**; JupyterLite still needs the gym-specific receipt/archive layer.
3. **Isolation and Stop:** put a value in exploration state, prove a check cannot see it, then stop a runaway check and run a new check successfully. This requires the separate worker under either editor.
4. **Teaching surface:** on `0059` and the MLP, measure slider-to-plot latency, tensor shape card readability, explicit training gate, keyboard/assistive-tech hint reveal, and browser memory under bounded training.

**Recommendation:** Keep JupyterLite provisionally for the specified first release because the hardest requirements are editor integration and precise attempt accounting. If a short marimo spike proves source capture and durable attempts without private/editor-internal APIs, prefer marimo for the lesson surface and simpler `.py` authoring. This recommendation is conditional; the research alone does not justify claiming marimo lacks the needed features.
